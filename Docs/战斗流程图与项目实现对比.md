# 战斗流程图与项目实现对比

更新日期：2026-08-03  
对比对象：`微信图片_20260803231224_254_2.jpg` 与当前 Unity 项目的战斗代码、卡牌 JSON、ScriptableObject、`Card`/`PreBattle` 场景及现有战斗文档。

## 1. 结论先行

当前项目已经具备一套比流程图更复杂的战斗规则层，包括卡牌实例、抽弃牌、战斗内强化、魔法点累计、大招事件、韧性击破、分级处决、敌方卡组、敌方 AI、多敌人数据结构、战后奖励和大量卡牌效果。

但是，流程图与当前实现并不是同一版规则，且存在几处会直接中断或改变实际战斗的高优先级差异：

1. **牌组数量不同**：图中开局 15 张；当前 `PreBattle` 和 `Card` 场景使用的规则要求 5 张，`Card` 场景调试列表却又放了 6 张。
2. **韧性击破逻辑不同且当前会卡住**：图中韧性归零后直接造成 300 点伤害；项目改成“强制确认处决”，但场景没有任何 `ConfirmExecution()` 按钮或调用点，击破后会停在 `AwaitingExecutionConfirmation`。
3. **大招规则完全不同**：图中大招 150 点并返还 3 点魔法；项目当前大招伤害为 0、附加 1 回合眩晕、不返还魔法，触发条件也改成“累计消耗 3 点”。
4. **第二只魔手未完成**：图中第二只魔手允许一回合用 2 点魔法，并有“三次后放大招/废弃”的流程；项目只有 `summon_companion` 数据和“召唤另一只魔手持续 3 回合”的卡牌说明，规则层会发出 `EffectNotImplemented`。
5. **当前敌方卡牌 AI 绕过多项防御规则**：跳过敌方回合、眩晕、攻击无效次数、百分比减伤和反伤主要只在 `ResolveEnemyAttack()` 中生效；当前场景敌人实际通过 `PlayEnemyCard()` 出牌，这条路径没有统一执行上述判定。
6. **玩家身上的流血/中毒不会结算**：敌方卡牌可以给玩家加流血和中毒，但回合开始只对敌人调用状态 tick，玩家状态会一直挂着而不扣血。
7. **战败闭环缺失**：图中明确进入战败过场；项目只有失败事件、停止 BGM 和失败特效，没有战败弹窗、重试或场景跳转。
8. **已有说明文档与代码也不一致**：现有文档仍混有 8/43 张牌、15 张牌组、强化保持整场、毒未实现、大招返蓝等旧规则；当前实际数据是 42 种卡牌、按 `copies` 共 64 份牌库拷贝、强化只保留到下一次使用/弃牌、大招不返蓝。

因此，当前最需要的不是继续往流程图里加表现层节点，而是先确定哪一版规则是最终标准，再统一规则层、场景接线、测试和文档。

## 3. 从流程图还原出的规则基线

图中文字较密，以下是按分区放大识别后得到的主流程。个别小字可能需要原图作者再次确认，但不影响主要差异判断。

### 3.1 战斗开始与玩家回合

1. 战斗开始时牌库有 15 张牌。
2. 抽 4 张；牌库不足 4 张时先抽剩余牌，再把弃牌堆洗入牌库，补到 4 张。
3. 玩家回合开始时有 3 点魔法点、3 点行动点。
4. 未使用的行动点不累积到下回合，下回合仍为 3 点。
5. 回合结束时未使用手牌进入弃牌堆。
6. 强化后的牌若没有使用，进入弃牌堆后强化不保留；使用强化牌后也只结算本次强化数值。

### 3.2 魔法点、强化、第二只魔手和大招

1. 普通情况下，一个魔手每回合可使用 1 点魔法点。
2. 拥有第二只魔手时，本回合可使用 2 点魔法点。
3. 魔法点用于激活/强化或使用魔法牌。
4. 图中大招造成 150 点伤害，并返还 3 点魔法点。
5. 图中还有“第二只魔手已使用 3 次后放大招并废弃”的结算分支。
6. 使用过的魔法牌从本场战斗移除，而不是进入弃牌堆循环。

### 3.3 伤害、韧性、防御和状态

1. 目标有防御值时，先扣防御值，再扣生命值。
2. 怪物韧性归零时，图中直接对怪物造成 300 点伤害。
3. 流血为 `x` 层时造成 `x` 点伤害，然后层数减 1。
4. 中毒持续 `x` 回合，每次造成 25 点伤害，然后回合数减 1。
5. 图中有“伤害降低 5，持续 x 回合”的状态。
6. 图中有敌方回合跳过效果。
7. 图中有攻击无效次数：怪物本次攻击变为 0，次数减 1。

### 3.4 回合结算与胜负

1. 玩家回合结束后结算玩家身上的流血、中毒及死亡。
2. 敌人回合先判断是否跳过，再判断攻击无效、防御和生命伤害。
3. 敌方行动后结算怪物身上的流血、中毒及死亡。
4. 怪物生命归零时胜利并计算奖励。
5. 玩家生命归零时失败并进入战败过场。

## 4. 两边已经一致或基本一致的部分

| 流程项 | 项目现状 | 结论 |
|---|---|---|
| 每回合抽 4 张 | `cardsDrawnPerTurn = 4`，`BeginPlayerTurn()` 固定抽 4 张 | 一致 |
| 抽牌堆不足时洗弃牌堆继续抽 | `DeckState.Draw()` 支持一次多抽过程中的中途洗牌 | 一致，并有测试 |
| 行动点基础值为 3 | 当前有效 `CombatRules.asset` 为 3 | 一致 |
| 行动点不跨回合累积 | 每回合调用 `RestoreActionPoints()` 恢复到有效上限 | 一致 |
| 回合结束弃掉未使用手牌 | `EndPlayerTurn()` 调用 `DeckState.DiscardHand()` | 一致 |
| 使用的普通牌进入弃牌堆 | `PlayCard()` 结算后弃牌 | 一致 |
| 强化消耗魔法点，不直接打出牌 | `UpgradeCard()` 扣魔法点后，牌仍留在手牌 | 一致 |
| 强化只影响这张运行时实例 | 每张牌有独立 `CardInstance` | 一致 |
| 强化不永久保留 | 使用或回合末弃牌时都会 `ConsumeUpgrade()` | 与图一致；与旧文档不一致 |
| 每回合通常最多消耗 1 点魔法 | `MaximumManaSpendPerTurn = 1`，强化和魔法牌共享额度 | 基础规则一致 |
| 有防御时先消耗防御 | `BlockPoints` 在生命扣减前吸收伤害 | 基本一致 |
| 流血层数递减 | 当前 tick 为“层数伤害，然后层数减 1” | 对敌人一致 |
| 跳过敌方回合 | 有 `SkipEnemyTurns` 状态 | 规则对象存在，但卡牌 AI 路径未正确执行 |
| 攻击无效次数 | 有 `NullifyAttackCharges` | 固定攻击路径一致，卡牌 AI 路径未正确执行 |
| 生命归零后判断胜负 | `EvaluateOutcome()` 产生 `Victory`/`Defeat` | 核心判断存在 |
| 胜利计算奖励 | 有金币、材料和随机卡牌奖励弹窗，确认后返回咖啡店 | 项目实现比图更具体 |

## 5. 项目中有，但流程图中没有的内容

### 5.1 战斗规则层新增内容

1. **明确的阶段状态机**：`NotStarted`、`PlayerTurnStart`、`PlayerInput`、`ResolvingCard`、`AwaitingExecutionConfirmation`、`PlayerTurnEnd`、`EnemyTurn`、`Victory`、`Defeat`。
2. **非法操作拒绝**：错误阶段、资源不足、目标无效、牌不在手中等都会返回 `ActionRejected`。
3. **手牌上限与溢出弃牌**：当前手牌上限 10，超过上限的新牌直接进弃牌堆。
4. **多敌人数据结构和目标 ID**：规则层支持多个敌人和按 ID 指定目标，图中是单个怪物流程。
5. **行动点修正**：`ActionPointModifier` 可以改变后续回合行动点上限。

## 7. 两边都有，但语义不一致的内容

### 7.1 牌组规模

- 图：15 张开局牌组。
- 当前有效配置：`ExpectedInitialDeckSize = 5`。
- 当前 `Card` 场景调试牌组：6 张，直接进场时只警告、不阻止开战。
- 当前 JSON：42 种卡牌，`copies` 合计 64 份；这不是单局牌组大小。

**需要决定**：正式单局牌组到底是 5 张还是 15 张。决定后必须同时修改规则资源、战前槽位、场景调试牌组、测试和文档。

### 7.2 魔法点恢复与大招触发

- 图：玩家回合开始显示 3 点魔法；大招 150 点并返还 3 点；第二魔手改变当回合魔法使用量。
- 项目：开局 3/3 魔法；回合开始只重置“本回合消耗额度”，不会自动回满当前魔法；击破任意敌人韧性时回满；每累计消耗 3 点触发大招；大招 0 伤害、眩晕 1 回合、不返蓝。

**需要决定**：魔法是“每回合刷新资源”，还是“跨回合持有、靠击破/大招恢复的资源”。目前图和代码表达的是两种完全不同的经济循环。

### 7.3 韧性击破与处决

- 图：韧性归零后立即追加 300 点伤害。
- 项目：暂停玩家输入，等待确认；小兵直接死亡，精英/Boss 按配置追加伤害和眩晕；未死则恢复韧性。
- 当前有效规则资源中精英/Boss 处决伤害和眩晕都是 0，且没有场景确认入口。

**需要决定**：保留图中的自动 300 点，还是保留项目中的交互式分级处决。若保留项目版本，必须先补确认 UI 和明确精英/Boss 数值。

### 7.4 魔法牌去向

- 图：使用后本场战斗移除。
- 项目：使用后进入弃牌堆，牌库用尽时可洗回。

这会显著改变魔法牌强度和循环频率，需要作为规则选择，而不是实现细节处理。

### 7.5 状态结算时机与公式

- 图：玩家回合结束结算玩家状态，敌方行动后结算怪物状态。
- 项目：下一次玩家回合开始时，只结算所有存活敌人的流血和中毒。
- 流血公式基本一致。
- 中毒公式不同：图为固定 25 点/回合；项目为当前层数点伤害。
- 玩家状态在项目中没有 tick。

### 7.6 减伤

- 图：固定减少 5 点，持续 `x` 回合。
- 项目：按百分比向上取整，玩家卡牌路径硬编码 1 回合；状态对象虽然能保存持续回合，但当前数据没有对应卡牌。

### 7.7 敌人行动模型

- 图：怪物执行一次攻击，并经过跳过、攻击无效、防御、生命等统一判定。
- 项目当前场景：敌人每回合抽 2 张、最多出 2 张，按总伤害排序，使用 2 点基础行动点；没牌才走固定攻击。

当前项目把“固定攻击”和“卡牌攻击”拆成两条规则入口，导致相同防御状态的效果不一致，是目前最危险的结构差异之一。

## 8. 当前项目内部还存在的断点和风险

这些问题不一定直接写在图中，但会影响“项目当前已经做到什么”的判断。

### P0：会中断战斗或让核心规则失效

#### 8.1 处决确认没有场景入口

代码搜索结果中，`ConfirmExecution()` 只在 `BattleController` 暴露，没有运行时脚本或 `Card.unity` 按钮调用。击破韧性后：

1. 阶段切到 `AwaitingExecutionConfirmation`；
2. 继续出牌会被拒绝；
3. 结束回合也会被拒绝；
4. 玩家没有可见的确认操作。

这是确定的战斗软锁。

#### 8.2 当前敌方卡牌 AI 没有统一经过防御判定

当前有效敌人 `Enemy_Minion.asset` 有 6 张敌方卡牌，场景启用 `CardEnemyAI`。但 `PlayEnemyCard()`/`ResolveEnemyCardEffects()` 与 `ResolveEnemyAttack()` 的判定不一致：

- 不检查 `IsCurrentEnemyTurnSkipped`；
- 不消耗敌人的眩晕回合；
- 不消耗玩家的攻击无效次数；
- 不应用玩家的百分比减伤；
- 不触发玩家的反伤；
- 只应用了 `BlockPoints`。

结果是图中“跳过回合—攻击无效—防御—生命”的核心链条，在当前主要敌人行动路径上并不成立。

#### 8.3 玩家流血/中毒永远不 tick

敌方卡牌路径可以 `AddBleedStacks()` 和 `AddPoisonStacks()` 给玩家，但 `BeginPlayerTurn()` 只遍历 `State.Enemies`。这会让敌方流血/中毒牌只有图标或层数，没有实际持续伤害。

#### 8.4 眩晕对当前卡牌敌人无效

大招和处决可以给敌人增加 `StunTurns`，但只有固定攻击入口 `ResolveEnemyAttack()` 会 `ConsumeOneStunTurn()`；当前卡牌 AI 直接 `PlayEnemyCard()`，因此仍会正常出牌。

### P1：规则存在，但数值或流程未定

#### 8.5 当前大招实际伤害为 0

大招事件和眩晕会产生，但图中的 150 点伤害没有配置。场景也没有专门处理 `UltimateTriggered` 的 UI/VFX，玩家可能只看到状态变化，无法理解为什么触发。

#### 8.6 精英/Boss 处决有效配置为 0

代码默认构造值和测试使用 40 点/眩晕 1 回合，但当前场景引用的 `Assets/Settings/PlayTime/CombatRules.asset` 中精英/Boss 处决伤害与眩晕均为 0。若以后把当前敌人等级改为精英或 Boss，确认处决后可能只恢复韧性而没有有效收益。

#### 8.7 召唤牌可进入正式牌库但效果未实现

`magic_summon` 是当前 42 张卡中的正式卡牌，效果为 `summon_companion`；玩家可以在战前选中并在战斗中消耗魔法打出，但只会收到未实现事件。

#### 8.8 战败没有出口

胜利有完整奖励弹窗与返回 `Cafe`；失败只有事件、BGM 停止和 VFX，没有失败界面、重试、返回或时间推进规则。

#### 8.9 敌方卡牌导致玩家死亡后阶段会被改回 EnemyTurn

`PlayEnemyCard()` 调用 `EvaluateOutcome()` 后，即使已经产生失败并切到 `Defeat`，分支仍会再次 `SetPhase(EnemyTurn)`。`Outcome` 仍是 `Defeat`，但 `Phase` 与结果不一致，可能影响 UI 或后续调用。

### P2：工程一致性和维护风险

#### 8.10 场景中有两套 BattleController/AI

`Card.unity` 中存在：

- 一套禁用的 `BattleController`，引用测试敌人且 `autoStartBattle = false`；
- 一套启用的 `BattleController`，引用 `Enemy_Minion` 且 `autoStartBattle = true`；
- 禁用控制器所在对象上的 `CardEnemyAI` 组件仍为启用状态，但引用禁用控制器。

当前主要流程由第二套控制器运行，但保留重复对象容易让后续 Inspector 修改改错目标。

#### 8.11 调试牌组数量与规则不一致

有效规则要求 5 张，启用控制器的调试列表有 6 张。直接打开 `Card` 场景仍允许开战，只输出警告；从 `PreBattle` 进入时则严格要求 5 张。

#### 8.12 现有文档严重过期

至少存在以下旧描述：

- 8 张牌/15 张牌组；
- 43 张牌；
- 强化状态保持整场战斗；
- 中毒仍待实现；
- 大招返还 3 点魔法；
- 玩家没有护盾/防御值；
- `CardData` 与当前 `CardDataV2` 路径混用。

这些与当前代码、JSON 或场景配置冲突，后续开发很容易依据错误文档继续扩展。

#### 8.13 部分规则有代码但缺测试

现有测试覆盖抽牌洗牌、手牌溢出、行动点、出牌、强化、耗蓝限制、大招触发、韧性回蓝、流血/中毒（敌人）、格挡反伤和分级处决。

缺少或明显不足的测试包括：

- 玩家身上的流血/中毒；
- 敌方卡牌路径下的跳过、眩晕、攻击无效、减伤和反伤；
- 魔法牌移除或弃牌的最终规则；
- 第二魔手/召唤；
- 失败后的阶段和转场；
- 多敌人行动顺序；
- 枪械逐发过程中目标提前死亡、取消和回合结束；
- 场景中处决确认 UI 的集成测试。

## 9. 建议的实施顺序

### 第一阶段：先定规则，不急着改代码

需要产品/策划明确以下 7 个选择：

1. 单局牌组是 5 张还是 15 张？
2. 韧性击破是自动 300 点，还是交互式分级处决？
3. 大招是 150 点并返蓝，还是 0/可配置伤害加眩晕且不返蓝？
4. 魔法点是每回合回满，还是跨回合持有并靠击破恢复？
5. 魔法牌使用后移除，还是进入弃牌堆循环？
6. 中毒是固定 25 点/回合，还是按层数递减伤害？
7. 第二只魔手的获得方式、持续时间、每回合魔法额度和“三次后”的准确语义是什么？

### 第二阶段：修复不依赖策划选择的 P0 断点

1. 把敌方固定攻击和敌方卡牌伤害统一进同一条“攻击前状态—防御—伤害—反伤—死亡”管线。
2. 让跳过回合和眩晕在敌方卡牌 AI 开始行动前生效。
3. 为玩家和敌人都建立统一的状态 tick 时机。
4. 若暂时保留确认处决，立即补确认 UI；若还未定规则，至少增加开发期自动确认或醒目的阻塞提示，避免无反馈软锁。
5. 修正敌方卡牌致死后 `Phase` 被改回 `EnemyTurn` 的问题。

### 第三阶段：实现最终规则

1. 按决定统一大招伤害、返蓝、魔法点恢复与第二魔手。
2. 按决定统一处决伤害、确认方式、精英/Boss 数值和韧性恢复。
3. 按决定实现魔法牌移除区，或明确继续使用弃牌堆。
4. 完成 `summon_companion`；如果暂不做，应先从可选牌池隐藏召唤牌。
5. 完成战败 UI、转场和重试/返回逻辑。

### 第四阶段：清理和回归

1. 删除或明确标注 `Card.unity` 中的旧控制器对象。
2. 统一调试牌组数量。
3. 更新现有战斗设计、代码职责和 JSON 配置文档。
4. 为上面的 P0/P1 规则补 EditMode 和场景集成测试。
5. 最后再更新战斗流程图，使它成为当前实现的唯一规则总览。

## 12. 最终判断

这张流程图仍然适合作为“战斗体验主干”，但它对应的是一套较早、较简单的规则版本。当前项目已经在卡牌数据、敌方卡组、处决、资源、奖励和表现层上扩展了很多内容，同时也产生了几条互相绕开的结算路径。

最优先应解决的是：

1. 定下 5/15 张牌、大招、处决、魔法恢复、魔法牌去向、中毒和第二魔手的最终规则；
2. 修复处决软锁；
3. 统一敌方攻击管线；
4. 补玩家状态 tick；
5. 补战败出口；
6. 再同步代码、测试、文档和新版流程图。

在这些问题明确前，继续单独扩充任一侧都会让流程图与项目进一步分叉。
