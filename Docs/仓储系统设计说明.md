# 仓储系统设计说明

## 目标

仓储系统把项目内数据分成两类：

- 静态仓储：项目内固定 JSON 数据，例如玩家卡牌、敌人卡牌、敌人卡组分类。
- 动态仓储：运行时临时数据，例如玩家当前选牌、战斗奖励卡牌、咖啡选择、金币和材料资源。

外部系统应优先通过统一仓储读写数据，避免在 UI、战斗、奖励结算中各自创建零散的静态列表或临时集合。

## 当前实现

### StaticGameRepository

位置：`Assets/Script/Combat/Repository/StaticGameRepository.cs`

职责：

- 接收 `CardDatabaseService` 加载完成后的 `CardJsonRepository`。
- 缓存全部卡牌、玩家卡牌、敌人卡牌。
- 按 `category` 提供只读卡牌列表。
- 通过 `cardId` 查询卡牌定义。

常用入口：

- `StaticGameRepository.PlayerCards`
- `StaticGameRepository.EnemyCards`
- `StaticGameRepository.GetCardsByCategory(category)`
- `StaticGameRepository.TryGetCard(cardId, out card)`
- `StaticGameRepository.GetRequiredCard(cardId)`

静态仓储只保存定义数据，不保存玩家状态。

### RuntimeGameRepository

位置：`Assets/Script/Combat/Repository/RuntimeGameRepository.cs`

职责：

- 保存当前已选战斗卡牌 ID。
- 保存当前选择的 Demo 战斗阶段。
- 保存当前选择的咖啡 ID。
- 保存战斗获得的卡牌 ID 和玩家拥有卡牌数量。
- 统一金币和材料资源的写入、消费、查询入口。

常用入口：

- `SetSelectedDeck(cardIds)`
- `SelectedCardIds`
- `ClearSelectedDeck()`
- `SetSelectedDemoStage(stage)`
- `SelectedDemoStage`
- `SetSelectedCoffees(coffeeIds)`
- `AddBattleRewardCard(cardId, amount)`
- `GetOwnedCardCopies(cardId)`
- `AddGold(amount)`
- `SpendGold(amount)`
- `AddResource(resourceId, amount)`
- `SpendResource(resourceId, amount)`
- `GetResourceAmount(resourceId)`
- `ResetRunState()`

动态仓储只保存 ID 和数量。需要显示名字、图片、效果时，再通过 `StaticGameRepository` 根据 ID 查询定义。

## 数据生命周期

- 新开 Play Session：`DemoFlowState` 会清空当前选牌和选择的 Demo 阶段。
- 战斗前：`CardSelectionUI` 从 `RuntimeGameRepository.SelectedCardIds` 恢复上一次选牌。
- 点击开始战斗：`CardSelectionUI` 将当前选牌写入 `RuntimeGameRepository.SetSelectedDeck`。
- 战斗初始化：`BattleController` 从 `RuntimeGameRepository.SelectedCardIds` 读取卡牌 ID，再通过 `StaticGameRepository.GetRequiredCard` 创建战斗用 `CardInstance`。
- 战斗胜利：`HuntResultPresenter` 把金币、材料、奖励卡牌写入 `RuntimeGameRepository`。
- 战斗结束回战前：已选牌保留，玩家可以继续修改。
- 重置 Demo：清空当前选牌和 Demo 阶段。

## 与旧代码的替代关系

已替换：

- `BattleSession` -> `RuntimeGameRepository`
- `PlayerCardCollection` -> `RuntimeGameRepository`
- `HuntResultPresenter.AddInventoryResource` -> `RuntimeGameRepository.AddResource / AddGold`
- 直接遍历 `cardDatabase.Repository.Cards` -> `StaticGameRepository`

保留：

- `CardJsonRepository`：仍负责 JSON 解析和校验。
- `CardDatabaseService`：仍负责从 `StreamingAssets/CardDataV2` 加载卡牌 JSON。
- `InventorySystem`：仍是现有咖啡厅 UI 监听的资源容器。`RuntimeGameRepository` 会把金币和材料操作转发给它，保证 `CoinUI`、`IngredientUI` 等旧 UI 正常刷新。

## 扩展约定

新增 JSON 数据时，优先新增静态仓储索引：

1. 保持 JSON 解析类只负责解析和校验。
2. 在加载服务完成后注册到静态仓储。
3. UI 和玩法逻辑通过静态仓储查询，不直接复制完整数据列表。

新增运行时状态时，优先新增动态仓储 API：

1. 动态仓储保存 ID、数量、当前选择、临时奖励等轻量状态。
2. 不把完整 `CardSpec`、敌人定义、奖励定义长期放进动态仓储。
3. 明确清空时机，例如新开游戏、重置 Demo、单场战斗奖励开始前。
4. 如果需要持久化存档，以后可以从 `RuntimeGameRepository` 的快照 API 统一导出。

## 当前接入点

- `CardSelectionUI`：读取玩家静态卡牌列表，恢复和提交当前选牌。
- `CoffeeSelectionUI`：提交当前选择的咖啡。
- `BattleController`：读取当前选牌和咖啡，创建战斗牌组和咖啡槽。
- `HuntResultPresenter`：写入战斗胜利奖励。
- `Rewarder`：写入咖啡订单金币。
- `CustomerController`：写入 NPC 回访金币。
- `CollectController`：写入采集材料。
- `CardDealTest`：通过静态仓储读取测试卡牌。
