# 静态 JSON 区域场景与基础仓储系统任务文档

更新日期：2026-07-30  
适用范围：城市区域第一阶段  
文档状态：需求基线，可用于后续拆分开发任务  

## 1. 文档目的

本文档统一说明以下两项工作的目标、边界、数据归属、实施顺序和验收标准：

1. 建立基础仓储与玩家存档系统，为金币、材料、卡牌、配方、装备和永久状态提供统一存储位置。
2. 建立由静态 JSON 驱动的区域场景管理系统，让玩家从五个地图点中选择事件区、宝藏区或战斗区，并加载对应内容。

第一阶段只实现当前城市地图，不扩展其他大区域，不要求正式美术素材，不在本阶段制作复杂仓库 UI。

## 2. 总体结论与实施顺序

建议先建立“最小可用基础仓储系统”，然后接入区域场景系统。

原因如下：

- 事件、宝藏和战斗都会修改金币、卡牌、配方、装备、材料和玩家属性。
- 每日地图、三次探索进度、不重复内容池和剧情标记都需要跨场景保存。
- 如果先做区域场景而没有统一存储，奖励和世界状态会分散在静态变量、PlayerPrefs 和各场景脚本中，后续必然返工。
- 基础仓储不等于完整背包功能。第一阶段只实现数据存储、查询、增减、保存和恢复，不制作筛选、排序、拖拽、装备强化等复杂界面。

推荐实施顺序：

1. 玩家存档与基础仓储 V1。
2. 区域静态 JSON 数据结构。
3. 每日地图类型生成与三次探索流程。
4. 事件、宝藏、战斗三类内容处理器。
5. 内容不重复机制、条件事件和完整存档恢复。
6. 美术素材、动画和表现层替换。

## 3. 已确认需求基线

### 3.1 批注意见对应结论

1. 每天的具体地图结果不由 JSON 直接指定。JSON 只提供候选内容、权重、条件和配置；运行时使用随机数生成结果。
2. 每个游戏日的五个地图点固定包含：1 个事件区、1 个宝藏区、3 个战斗区。
3. “每天”指游戏内天数，不使用现实日期。
4. 图片中“1 事件 + 1 宝藏 + 2 战斗”的旧描述作废，以五点的 `1 + 1 + 3` 为准。
5. 地图上提前显示三种区域类型，但不显示具体事件、宝藏或敌人。当前可使用紫、黄、红占位，后续替换为专门美术素材。
6. 事件中主动打出的卡牌默认只参与本次事件判定，不从玩家永久卡牌仓库中删除，也不改变玩家选定牌组。若未来需要“永久失去卡牌”的事件，必须由独立效果明确声明。
7. 事件判定由玩家从抽出的五张牌中主动选择并打出，不由系统自动检查牌组。
8. 同一内容池在一个轮次内不重复；所有当前可用内容都出现过后，清空该池的已使用记录并开始新一轮。
9. 金币、卡牌、配方、装备和材料先保存到玩家专用运行时 JSON 存档，不修改 StreamingAssets 下的静态配置。
10. 玩家每天最多探索三个地图点。
11. 玩家完成第三次探索后进入下一游戏日；前两次探索完成后返回同一天的地图。
12. 第一阶段只制作当前城市及图片所列的事件、宝藏和战斗内容，不提前建设多区域世界地图。

### 3.2 当前仍采用的默认规则

以下规则尚未被单独确认，为保证任务可以执行，第一阶段先采用推荐默认值：

- 五个点只随机“类型位置”；具体内容在玩家点击该点时才抽取。
- 玩家点击节点后，系统先确定并保存具体内容，再加载场景，避免强制退出或读档后重新随机。
- 当天只探索五个点中的三个，剩余两个随下一游戏日刷新。
- 未被玩家点击的节点不抽取具体内容，因此不会消耗事件、宝藏或敌人内容池。
- 已完成的节点当天不可再次进入。
- 事件使用玩家在战前准备界面左侧选择的同一套牌组。
- 事件从该牌组的临时副本中洗牌并抽取五张；事件结束后临时抽牌状态销毁。
- 如果五张牌中没有能够触发正面分支的牌，显示该事件定义的失败、离开或放弃分支。
- 事件卡牌默认不会永久消耗；需要永久移除时使用专门的 `remove_owned_card` 类效果。
- 在第三次探索结算和存档成功后，才推进游戏日，防止结算失败导致天数和奖励不同步。

## 4. 系统边界

### 4.1 静态 JSON 负责的内容

静态 JSON 位于 `Assets/StreamingAssets`，作为策划配置，只读加载：

- 区域名称、区域类型和颜色/图标资源 ID。
- 事件、宝藏、战斗候选内容。
- 内容权重和出现条件。
- NPC、对白、背景、立绘和音乐资源 ID。
- 玩家可主动打出的牌型和对应结果。
- 敌人组、奖励池和战斗等级。
- 金币、材料、卡牌、配方、装备和属性变化效果。
- 内容是否允许重复、是否只能触发一次。

静态 JSON 不保存：

- 今天五个地图点实际落在什么位置。
- 玩家今天点击过哪些点。
- 玩家当前拥有多少金币和物品。
- 玩家解锁了哪些配方和卡牌。
- 守夜人是否死亡、小偷是否已经解锁等世界状态。
- 当前游戏日和本日探索次数。

### 4.2 Unity 代码和场景负责的内容

- 生成随机数并从候选池中选择内容。
- 解析、验证和缓存 JSON。
- 加载通用事件、宝藏或战斗场景。
- 根据配置绑定文字、按钮、敌人和奖励。
- 执行受控的条件与效果。
- 播放 UI、动画、音效和转场。
- 将运行时状态写入玩家存档。

JSON 不直接保存 C# 方法名、Unity 场景对象路径或任意反射调用。所有条件和效果必须来自程序支持的有限类型，避免配置可以执行不可控逻辑。

## 5. 推荐目录与数据文件

### 5.1 静态配置

建议新增：

```text
Assets/StreamingAssets/AreaData/
  manifest.json
  city/
    area.json
    events.json
    treasures.json
    encounters.json
    reward_tables.json
    area-data.schema.json
```

职责建议：

- `manifest.json`：数据版本、城市文件列表、预期内容数量。
- `area.json`：五个节点组成、每日探索次数、区域显示信息、场景模板 ID。
- `events.json`：黑市、守夜人、小偷、神秘客人等事件。
- `treasures.json`：装备、金币、配方、永久生命、隐藏战斗等宝藏。
- `encounters.json`：小怪、精英、Boss 敌人组和权重。
- `reward_tables.json`：战斗掉落、卡牌奖励、素材和金币范围。
- `area-data.schema.json`：字段、枚举、必填项和数值范围。

### 5.2 运行时玩家存档

第一阶段推荐每个存档槽使用一个完整快照文件：

```text
Application.persistentDataPath/
  Saves/
    slot_01/
      save.json
      save.backup.json
```

不建议第一阶段把金币、卡牌、世界进度拆成多个互不关联的存档文件。一次事件可能同时修改金币、卡牌和剧情标记；单快照更容易保证全部成功或全部失败，避免文件之间状态不一致。

程序内部仍然可以按职责拆成仓储、卡牌、配方、装备、玩家属性和世界进度等模块，对外保存时合并为一个 `save.json`。

## 6. 基础仓储与玩家存档 V1

### 6.1 保存内容

玩家存档至少包含：

- 存档版本和存档槽 ID。
- 当前游戏日。
- 当天已探索次数。
- 当天五个地图点的类型、完成状态和已确定内容 ID。
- 当前远征选择的牌组 ID 列表。
- 金币和可堆叠材料数量。
- 玩家拥有的卡牌 ID 与数量。
- 已解锁咖啡配方 ID。
- 装备实例列表。
- 当前生命、最大生命以及永久属性变化。
- 各内容池当前轮次的已使用内容 ID。
- 世界剧情标记，例如守夜人状态、小偷解锁状态、一次性事件状态。
- 当前场景恢复点和最近一次已完成结算编号。

### 6.2 仓储分类

#### 可堆叠资源

用于金币、素材和普通消耗品：

- 以稳定 `resourceId` 为键。
- 数量必须为整数。
- 除明确允许负数的系统外，结算后不得小于 0。

#### 卡牌收藏

- 静态卡牌属性仍从 CardDataV2 读取。
- 存档只记录 `cardId` 和拥有数量。
- 选定牌组单独记录卡牌 ID 列表，允许重复 ID。
- 事件临时抽出的牌不新增卡牌实例，不写入收藏。

#### 配方

- 静态配方内容仍从 CoffeeData 读取。
- 存档只记录已解锁配方 ID。
- 重复获得同一配方时必须有明确替代结果，第一阶段推荐转化为配置的金币或材料。

#### 装备

装备使用实例列表而不是简单数量，为后续装备槽、品质和随机属性预留空间：

- `instanceId`：玩家拥有的唯一实例 ID。
- `definitionId`：静态装备定义 ID。
- `equippedSlot`：未装备时为空。
- 第一阶段不要求强化、耐久和随机词条。

### 6.3 存档安全要求

- 保存时先写临时文件。
- 临时文件序列化和校验成功后再替换正式文件。
- 替换前保留上一份 `save.backup.json`。
- 加载失败时尝试读取备份。
- 静态配置和玩家存档都带 `schemaVersion`。
- 不认识的新版本不能静默加载。
- 一次结算生成唯一结算 ID，重复恢复时不能重复发放奖励。
- 玩家点击地图点后，在加载目标场景前保存抽中的内容 ID。
- 第三次探索必须先完成奖励保存，再推进游戏日。

### 6.4 第一阶段不做

- 仓库分页、筛选、排序和搜索 UI。
- 拖拽整理和格子容量。
- 物品重量。
- 装备强化、耐久、随机词条和套装。
- 多角色共享仓库。
- 云存档和跨设备同步。
- 多存档槽 UI；底层保留槽位概念即可。

## 7. 每日地图生成规则

### 7.1 类型位置生成

每天创建固定类型袋：

```text
Event, Treasure, Battle, Battle, Battle
```

使用游戏随机服务打乱后依次分配给 `MapPoint_1` 至 `MapPoint_5`。

生成结果写入当天地图状态。当天重新进入 PreBattle 时恢复原位置，不重新随机。

地图显示规则：

- 事件区：显示事件类型素材，当前可用紫色占位。
- 宝藏区：显示宝藏类型素材，当前可用黄色占位。
- 战斗区：显示战斗类型素材，当前可用红色占位。
- 不显示具体 NPC、宝藏种类或敌人名称。
- 已完成节点显示完成状态并禁用点击。

### 7.2 具体内容抽取

玩家点击未完成节点后：

1. 检查当天探索次数是否小于 3。
2. 检查节点是否未完成。
3. 根据节点类型取得对应 JSON 内容池。
4. 根据世界状态过滤不满足条件的内容。
5. 排除本轮已经出现过的内容。
6. 按剩余内容的权重生成随机数并选择一个内容。
7. 把内容 ID 写入节点状态并立即保存。
8. 创建本次 `AreaSession`。
9. 加载对应场景模板。

如果读取到节点已经有内容 ID，必须继续使用该内容，不得重新抽取。

### 7.3 不重复轮次

事件、宝藏和战斗分别维护自己的已使用集合：

- `eventPoolUsedIds`
- `treasurePoolUsedIds`
- `battlePoolUsedIds`

抽取规则为“带权不放回”：

- 内容被玩家实际进入后才加入已使用集合。
- 未访问节点不会消耗内容。
- 当前所有符合条件的内容都已使用后，清空该池的集合并开始新一轮。
- 尚未满足条件的内容不参与“本轮是否已全部使用”的判断。
- 新内容因剧情条件变为可用后，可以进入当前轮剩余候选。
- 永久一次性内容触发后写入世界标记，即使新一轮开始也不能再次进入候选。

## 8. 三次探索与场景流程

### 8.1 当日开始

1. 咖啡厅结束营业。
2. 进入 PreBattle。
3. 读取或创建当天五个地图点。
4. 玩家在左侧完成当日远征牌组选择。
5. 将牌组保存为 `ExpeditionSession.SelectedDeckIds`。

当前 BattleSession 只适合向单场战斗传递卡组，并可能在战斗初始化后清空。区域系统需要独立保存“当日远征牌组”，进入战斗时再复制给 BattleSession，确保事件和后续战斗仍能使用同一套牌。

### 8.2 第一次和第二次探索

1. 玩家点击地图点。
2. 系统确定具体内容并保存。
3. 进入事件、宝藏或战斗场景。
4. 完成结算。
5. 节点标记为完成。
6. 当日探索次数加 1。
7. 保存成功后播放转场并返回 PreBattle。

### 8.3 第三次探索

1. 按相同方式完成内容结算。
2. 当日探索次数变为 3。
3. 保存奖励和世界状态。
4. 清理当日临时远征状态。
5. 游戏日加 1。
6. 播放转场并进入咖啡厅。

## 9. 事件区域设计

### 9.1 通用事件场景

第一阶段使用一个通用事件场景，而不是每张事件卡创建一个 Unity Scene。

JSON 配置场景中的：

- 标题和区域名称。
- 主角、NPC、背景和音乐资源 ID。
- 对话 ID。
- 抽牌数量，当前固定为 5。
- 允许主动打出的牌型。
- 每种牌型对应的结果文本和效果列表。
- 无可用牌、放弃或离开分支。
- 结束后的转场目标。

### 9.2 事件牌组规则

- 来源为玩家在当日战前准备中选择的牌组。
- 每次事件建立临时牌组副本。
- 洗牌后抽取五张。
- 玩家主动选择并打出一张。
- 系统读取该牌的分类，例如近战、枪械、魔法、防御。
- 事件根据分类执行对应结果。
- 默认不消耗玩家永久卡牌，不修改选定牌组。
- 事件临时抽牌和弃牌状态在事件结束后销毁。

### 9.3 条件事件

例如小偷事件依赖守夜人永久消失，JSON 只声明条件，世界进度保存实际状态：

- `night_watchman_alive`
- `night_watchman_resolved`
- `thief_event_unlocked`

条件检查必须发生在随机抽取之前。未满足条件的内容不能被选中，也不能占用概率。

## 10. 宝藏区域设计

宝藏使用通用结算场景或弹窗，支持：

- 获得装备。
- 获得金币。
- 解锁咖啡配方。
- 永久增加最大生命。
- 进入隐藏战斗。

宝藏分类权重和具体奖励内容必须分成两层：

1. 先抽取宝藏分类。
2. 再从该分类的具体内容池中抽取一个内容。

这样“发现装备 30%，普通装备 12 张”表示先命中 30% 的装备分类，再从 12 张装备中抽取；不能让每一张装备都各自拥有 30% 概率。

隐藏 Boss 的 10% 与 2.5% 描述目前存在旧资料歧义。第一阶段数据录入前必须确定它们是：

- 宝藏分类本身占 10%，其中 2.5% 为隐藏 Boss；或
- 宝藏分类占 10%，隐藏 Boss 在该分类内另有独立权重。

## 11. 战斗区域设计

战斗区先按等级抽取：

- 小怪：60%。
- 精英：35%。
- Boss：5%。

再从该等级下尚未使用的敌人内容中带权抽取敌人组。

区域会话传递给战斗场景的数据至少包含：

- `encounterId`
- `enemyGroupId`
- `enemyRank`
- `rewardTableId`
- `returnScene`
- `mapPointId`
- `settlementId`
- 当日远征牌组 ID

战斗控制器需要从敌人组 ID 创建敌人，而不是只依赖 Inspector 中固定的敌人列表。战斗胜利后由统一奖励结算器写入仓储；战斗失败时不得发放胜利奖励。

## 12. 条件与效果执行器

第一阶段支持的条件类型建议包括：

- 是否拥有指定牌型或卡牌。
- 是否拥有足够资源。
- 世界标记是否存在或等于指定值。
- 内容是否已永久完成。
- 当前游戏日范围。
- 玩家当前生命或最大生命条件。

第一阶段支持的效果类型建议包括：

- 增加、扣除金币或材料。
- 获得卡牌。
- 永久移除卡牌。
- 解锁配方。
- 获得装备实例。
- 修改当前生命。
- 永久修改最大生命。
- 设置或清除世界标记。
- 标记一次性内容已完成。
- 开启商店。
- 开始指定战斗。
- 播放指定对话。
- 跳转地图或咖啡厅。

效果执行必须先校验整组操作是否可执行，再统一提交。不能出现“金币已扣除但卡牌发放失败”的半结算状态。

## 13. 组件职责建议

名称可在实现时调整，但职责必须保持分离：

- `SaveGameService`：加载、保存、备份、版本检查和原子写入。
- `PlayerRepository`：生命、最大生命和基础进度。
- `InventoryRepository`：金币、材料和普通物品数量。
- `CardCollectionRepository`：卡牌拥有数量和远征牌组。
- `RecipeRepository`：配方解锁。
- `EquipmentRepository`：装备实例和装备状态。
- `WorldProgressRepository`：游戏日、探索次数、世界标记和内容轮次。
- `AreaDatabaseService`：加载和验证 AreaData 静态 JSON。
- `DailyMapGenerator`：打乱固定类型袋，生成五点类型布局。
- `ContentRandomizer`：按条件、权重和不重复规则抽取具体内容。
- `AreaSession`：保存本次跨场景内容、节点和结算信息。
- `AreaSceneRouter`：按事件、宝藏、战斗类型加载场景。
- `AreaEffectExecutor`：校验并执行受控效果。
- `EventPresenter`：显示对话、五张牌和主动出牌结果。
- `TreasurePresenter`：显示宝藏并提交奖励。
- `BattleEncounterAdapter`：把敌人组与奖励表接入现有战斗系统。

## 14. 分阶段任务清单

### 阶段 A：需求与数据基线

- [ ] 将五点组成统一为 1 事件、1 宝藏、3 战斗。
- [ ] 将游戏日、每日三次探索写入唯一规则文档。
- [ ] 确认旧文档与当前图片冲突时，以哪一份内容数值为准。
- [ ] 确认宝藏隐藏 Boss 的两层概率。
- [ ] 为卡牌、敌人、资源、配方、装备、NPC、事件和奖励表建立稳定 ID 清单。
- [ ] 确认事件无有效牌时的失败或离开结果。

交付物：最终内容表、ID 表、概率表、条件标记表。

### 阶段 B：基础仓储与存档 V1

- [ ] 定义统一玩家存档模型和 `schemaVersion`。
- [ ] 实现存档加载、临时文件写入、正式文件替换和备份恢复。
- [ ] 实现金币与材料增减、查询、快照和恢复。
- [ ] 实现卡牌拥有数量和选定牌组存储。
- [ ] 实现配方解锁集合。
- [ ] 实现装备实例列表。
- [ ] 实现玩家生命、最大生命和永久属性变化。
- [ ] 实现世界标记、游戏日和探索次数。
- [ ] 实现统一事务式奖励提交。
- [ ] 添加新存档、正常保存、损坏恢复和重复结算测试。

验收标准：关闭游戏并重新进入后，所有仓储内容、玩家属性和游戏日完全恢复；同一结算不能重复领取。

### 阶段 C：区域静态数据管线

- [ ] 创建 AreaData 目录、manifest 和城市数据文件。
- [ ] 定义区域、事件、宝藏、战斗、奖励、条件和效果字段。
- [ ] 建立 JSON Schema。
- [ ] 实现 AreaDatabaseService。
- [ ] 校验版本、重复 ID、无效引用、空内容池、非法权重和未知效果。
- [ ] 为 JSON 加载和验证编写 EditMode 测试。

验收标准：数据错误能在进入 Play Mode 后明确指出文件名、内容 ID 和错误字段，不能带着半加载数据继续游戏。

### 阶段 D：每日地图与三次探索

- [ ] 生成并打乱固定五类型袋。
- [ ] 保存五个 MapPoint 的类型与完成状态。
- [ ] 根据类型显示紫、黄、红占位素材。
- [ ] 接入五个按钮点击。
- [ ] 点击时抽取具体内容并立即保存。
- [ ] 已完成节点禁用。
- [ ] 前两次探索返回原地图。
- [ ] 第三次探索结算成功后进入下一游戏日和咖啡厅。
- [ ] 重启游戏后恢复当天地图和探索次数。

验收标准：同一天反复进出场景，地图类型位置不变、已完成节点不恢复、已确定内容不重抽。

### 阶段 E：不重复内容随机器

- [ ] 为事件、宝藏、战斗分别保存已使用集合。
- [ ] 支持按条件过滤。
- [ ] 支持带权不放回抽取。
- [ ] 候选耗尽后自动开始新一轮。
- [ ] 支持永久一次性内容。
- [ ] 支持剧情解锁后加入当前候选。
- [ ] 编写固定随机种子测试和大样本权重测试。

验收标准：同一池全部可用内容出现前没有重复；进入下一轮后可以再次出现；未解锁内容不会被抽中。

### 阶段 F：事件区域 MVP

- [ ] 建立通用事件场景。
- [ ] 从当日远征牌组建立临时牌组并抽五张。

- [ ] 根据牌型选择 JSON 分支。

- [ ] 完成守夜人事件作为首个样例。
- [ ] 验证事件卡牌不会从永久收藏中消失。

验收标准：同一个事件仅靠替换 JSON 就能改变对白、可用牌型、奖励和世界标记，不需要新建专属事件脚本。

### 阶段 G：宝藏区域 MVP

- [ ] 支持永久最大生命提升。

验收标准：所有奖励进入统一仓储并可在重启后恢复。

### 阶段 H：战斗区域 MVP

验收标准：同一个战斗场景能加载至少两种不同敌人组和奖励表，Inspector 不再固定唯一敌人组合。

### 阶段 I：内容录入与表现

## 15. 测试矩阵

至少覆盖：

- 新游戏第一天生成的五点恰好为 1、1、3。
- 每天地图位置随机，但同一天读档不变化。
- 玩家只能探索三个点。
- 未访问的两个节点不会消耗具体内容池。
- 同一内容池一轮内不重复。
- 所有内容用尽后开启新一轮。
- 条件事件在未解锁时不能出现。
- 玩家主动打出的牌来自战前选定牌组。
- 事件牌不会永久消失。
- 事件奖励同时包含金币、卡牌和世界标记时全部成功或全部失败。
- 战斗奖励不会因重复读取结算场景而重复发放。
- 第三次探索奖励保存成功后才进入下一天。
- 存档损坏时能读取备份或给出明确错误。
- 静态 JSON 缺少 ID、权重非法或引用不存在时拒绝加载。
- 没有正式美术素材时仍可使用占位图完成全流程。

## 16. 完成定义

第一阶段完成必须同时满足：

- 城市地图每天稳定生成五个区域类型点。
- 玩家能看见类型并选择其中三个。
- 事件、宝藏和战斗的具体内容均由运行时随机数从 JSON 候选池抽取。
- 当天读档不能改变已经生成或已经点击的结果。
- 内容池实现完整一轮内不重复。
- 事件能从玩家远征牌组抽五张并由玩家主动出牌。
- 金币、材料、卡牌、配方、装备和永久属性拥有统一存储位置。
- 所有玩家数据保存在 persistentDataPath 的运行时 JSON 中。
- StreamingAssets 中的静态 JSON 在游戏运行时不被修改。
- 前两次探索返回地图，第三次探索进入下一游戏日和咖啡厅。
- 游戏关闭并重启后能够正确恢复仓储、世界标记、游戏日和当日进度。
- 功能在没有正式美术素材的情况下可完整测试。

## 17. 开发前最后待确认项

正式实现前还需要确认以下内容数值，但不影响先完成仓储和数据框架：

1. 旧 Word 文档和当前思维导图发生冲突时，哪一份是事件内容的最终来源。
2. 守夜人各牌型分支的最终金币、卡牌和最大生命奖励。
3. 宝藏隐藏 Boss 的准确概率层级。
4. 战斗失败后该地图点算“已消耗”还是允许重新挑战。
5. 玩家主动打出的事件牌是否需要进入一次表现用弃牌动画。
6. 重复获得已解锁配方时转换成什么奖励。
7. 扣除金币事件中金币不足时采用扣到 0、禁止选择还是进入另一结果。

在这些数值确定前，可以先完成阶段 B、C、D 的基础框架与测试。
